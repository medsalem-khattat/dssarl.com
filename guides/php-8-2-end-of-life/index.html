PHP 8.2 reaches end of life on 31 December 2026: check your WordPress plugins before your host upgrades you

1. What "end of life" means, and the dates

When a PHP version reaches end of life, it gets no more security fixes. Hosts then move sites to a newer version, sometimes on their own schedule; some offer paid extended support instead.

PHP versionSecurity fixes until
8.1ended 31 Dec 2025
8.231 Dec 2026
8.331 Dec 2027
8.431 Dec 2028
8.531 Dec 2029
8.631 Dec 2030 (released 19 Nov 2026)

Source: php.net, "Supported Versions" and "Unsupported Branches" pages, checked 21 Nov 2026.

If your site runs PHP 8.2 or older, plan the move now. Moving to 8.3 gives you security fixes until the end of 2027; 8.4 or 8.5 gives you longer. Check that your WordPress version supports the target: on 21 Nov 2026, the WordPress core handbook ("PHP Compatibility and WordPress Versions") lists PHP 7.4 to 8.5 as supported for WordPress 7.0 and 7.1. PHP 8.6 is not yet listed there.

Your PHP version is shown in Tools > Site Health > Info > Server.

2. The safe route

  1. Back up files and database, and make sure you know how to restore.
  2. Update first: WordPress, all plugins, all themes. Many PHP problems are already fixed in newer plugin versions.
  3. Use a staging copy if your host offers one (some hosting panels have a one-click staging site).
  4. Switch the PHP version on staging in your hosting panel (often under "PHP version", "PHP selector" or "PHP configuration").
  5. Test what matters: home page, a product page, cart, checkout with a test order, contact form, the admin screens you use daily.
  6. Read the error log (see below).
  7. If something breaks, switch back to the previous version in the hosting panel. Then fix the cause and try again.
  8. When staging is clean, do the same on the live site at a quiet hour, and keep the backup.

Turn on the WordPress error log (staging). Add these lines to wp-config.php, above "That's all, stop editing":

define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );
define( 'WP_DEBUG_DISPLAY', false );

Errors are written to wp-content/debug.log and are not shown to visitors. Remove the lines (or set them to false) when you are done. Your host may also show a PHP error log in the panel.

3. How to find the plugin that breaks

Read the error. A fatal error message or log line shows a file path. The folder after wp-content/plugins/ (or wp-content/themes/) is the culprit. WordPress also emails the site admin a link to recovery mode, which lets you log in with the faulty plugin paused.

Deactivate and test. On staging, deactivate all plugins, then reactivate them one by one, testing after each. No access to the admin? Rename the plugin's folder in wp-content/plugins/ with your host's file manager or FTP; WordPress then treats it as deactivated.

Scan before you switch. A PHP compatibility scanner reads the code of your plugins and themes, without running it, and lists the lines likely to cause errors or deprecation notices on the PHP version you choose. It helps you see problems before you switch, and tells you which plugin authors to contact.

How to choose one:

  • It supports the PHP versions you need, including 8.3, 8.4 and 8.5. Some older scanners stop at PHP 8.0; check the supported versions on the plugin's page.
  • It scans plugins and themes, including premium ones, on your own server (a local scan), so code you bought is checked too.
  • It does not hang on shared hosting: look for scans that run in steps or in the background rather than in one long request.
  • It is recently updated and tested with your WordPress version.
  • Read the plugin's own page (description, requirements, FAQ) before installing, and run it on staging first.

How to find them: in your WordPress admin, go to Plugins > Add Plugin and search for "PHP compatibility". Developers can also run a static analysis tool with PHP compatibility rules from the command line.

Every scanner has limits. Static scanners read code without running it. They can miss problems that only appear at run time (code built on the fly, encoded files, missing PHP extensions, server settings), and they can flag code that never runs on your site. A clean report is a good sign, not a guarantee. Always test on staging too.

4. Deprecated vs Fatal, in 5 lines

  • Fatal error: PHP stops. The page shows "There has been a critical error on this website" or goes blank. Fix it before switching.
  • Deprecated: the code still works on this version but will stop working in a future one. The site runs normally.
  • Warning / Notice: something unexpected, the page usually still loads. Worth fixing, rarely urgent.
  • A debug.log full of "Deprecated" lines (for example about dynamic properties) is common after an upgrade and does not mean the site is broken.
  • What to do: update the plugin; if there is no update, send the log line to its author; if the plugin is abandoned, replace it.

5. What to ask your host

  • Which PHP version will you move my site to, and on what date? Will you do it automatically?
  • Can I switch PHP myself in the panel, and switch back if something breaks? Until when?
  • Do you offer paid extended support for old PHP versions, and what does it cost?
  • Do I have a staging site? How do I create one?
  • Where can I see the PHP error log?
  • How do I restore a backup, and how far back do backups go?

Quick checklist

  • Current PHP version noted (Site Health)
  • Backup done, restore tested or known
  • WordPress, plugins and themes updated
  • Scan run, errors reviewed (warnings later)
  • Staging switched and tested, error log read
  • Live site switched; you know how to switch back

Fin de vie de PHP 8.2 le 31 décembre 2026 : vérifiez vos extensions WordPress avant que votre hébergeur ne change de version

1. Ce que veut dire « fin de vie », et les dates

Quand une version de PHP arrive en fin de vie, elle ne reçoit plus de correctifs de sécurité. Les hébergeurs migrent alors les sites vers une version plus récente, parfois selon leur propre calendrier ; certains proposent à la place un support prolongé payant.

Version de PHPCorrectifs de sécurité jusqu'au
8.1terminé le 31 déc. 2025
8.231 déc. 2026
8.331 déc. 2027
8.431 déc. 2028
8.531 déc. 2029
8.631 déc. 2030 (sortie le 19 nov. 2026)

Source : php.net, pages « Supported Versions » et « Unsupported Branches », consultées le 21 nov. 2026.

Si votre site tourne en PHP 8.2 ou plus ancien, préparez la migration dès maintenant. Passer en 8.3 vous assure des correctifs de sécurité jusqu'à fin 2027 ; 8.4 ou 8.5 vous donnent plus de marge. Vérifiez que votre version de WordPress supporte la cible : au 21 nov. 2026, le manuel WordPress (« PHP Compatibility and WordPress Versions ») indique PHP 7.4 à 8.5 comme supportés pour WordPress 7.0 et 7.1. PHP 8.6 n'y figure pas encore.

Votre version de PHP s'affiche dans Outils > Santé du site > Informations > Serveur.

2. La méthode sûre

  1. Sauvegardez fichiers et base de données, et sachez comment restaurer.
  2. Mettez à jour d'abord WordPress, toutes les extensions et tous les thèmes. Beaucoup de problèmes PHP sont déjà corrigés dans les versions récentes.
  3. Travaillez sur une copie de test (staging) si votre hébergeur en propose une (certains panneaux la créent en un clic).
  4. Changez la version de PHP de la copie de test dans le panneau d'hébergement (souvent « Version PHP », « Sélecteur PHP » ou « Configuration PHP »).
  5. Testez l'essentiel : accueil, une fiche produit, le panier, une commande test, le formulaire de contact, les écrans d'admin que vous utilisez chaque jour.
  6. Lisez le journal d'erreurs (voir ci-dessous).
  7. En cas de panne, revenez à l'ancienne version dans le panneau d'hébergement. Corrigez la cause, puis réessayez.
  8. Quand la copie de test est propre, faites la même chose sur le site en ligne, à une heure calme, en gardant la sauvegarde.

Activer le journal d'erreurs WordPress (sur la copie de test). Ajoutez ces lignes dans wp-config.php, au-dessus de « C'est tout, ne touchez pas à ce qui suit » :

define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );
define( 'WP_DEBUG_DISPLAY', false );

Les erreurs sont écrites dans wp-content/debug.log, sans être affichées aux visiteurs. Retirez ces lignes (ou passez-les à false) une fois terminé. Votre hébergeur affiche peut-être aussi un journal d'erreurs PHP dans le panneau.

3. Trouver l'extension qui casse le site

Lisez l'erreur. Le message d'erreur fatale, ou la ligne du journal, contient un chemin de fichier. Le dossier qui suit wp-content/plugins/ (ou wp-content/themes/) est le coupable. WordPress envoie aussi à l'administrateur un e-mail avec un lien vers le mode de récupération, qui permet de se connecter avec l'extension fautive mise en pause.

Désactivez et testez. Sur la copie de test, désactivez toutes les extensions, puis réactivez-les une par une en testant à chaque fois. Plus d'accès à l'admin ? Renommez le dossier de l'extension dans wp-content/plugins/ avec le gestionnaire de fichiers de l'hébergeur ou en FTP : WordPress la considère alors comme désactivée.

Analysez avant de changer de version. Un scanner de compatibilité PHP lit le code de vos extensions et thèmes, sans l'exécuter, et liste les lignes susceptibles de provoquer des erreurs ou des avertissements « Deprecated » sur la version de PHP choisie. Il vous montre les problèmes avant le changement et vous indique quels auteurs d'extensions contacter.

Comment en choisir un :

  • Il prend en charge les versions de PHP dont vous avez besoin, y compris 8.3, 8.4 et 8.5. Certains scanners anciens s'arrêtent à PHP 8.0 : vérifiez les versions prises en charge sur la fiche de l'extension.
  • Il analyse les extensions et les thèmes, y compris premium, sur votre propre serveur (analyse locale), pour que le code acheté soit vérifié aussi.
  • Il ne bloque pas sur un hébergement mutualisé : privilégiez une analyse par étapes ou en arrière-plan plutôt qu'en une seule longue requête.
  • Il est mis à jour récemment et testé avec votre version de WordPress.
  • Lisez la fiche de l'extension (description, prérequis, FAQ) avant de l'installer, et lancez-la d'abord sur la copie de test.

Où les trouver : dans l'admin WordPress, allez dans Extensions > Ajouter une extension et cherchez « PHP compatibility ». Les développeurs peuvent aussi lancer en ligne de commande un outil d'analyse statique avec des règles de compatibilité PHP.

Tout scanner a ses limites. Un scanner statique lit le code sans l'exécuter. Il peut rater des problèmes qui n'apparaissent qu'à l'exécution (code généré à la volée, fichiers chiffrés, extension PHP manquante, réglages du serveur) et signaler du code qui ne tourne jamais sur votre site. Un rapport propre est bon signe, pas une garantie. Testez toujours aussi sur une copie de test.

4. « Deprecated » ou erreur fatale, en 5 lignes

  • Erreur fatale (Fatal error) : PHP s'arrête. La page affiche « Il y a eu une erreur critique sur ce site » ou reste blanche. À corriger avant de changer de version.
  • Deprecated (obsolète) : le code fonctionne encore sur cette version mais cessera de fonctionner dans une version future. Le site tourne normalement.
  • Warning / Notice (avertissement) : quelque chose d'inattendu, la page se charge en général. À corriger, rarement urgent.
  • Un debug.log rempli de lignes « Deprecated » (par exemple sur les propriétés dynamiques) est courant après une mise à jour de PHP et ne veut pas dire que le site est cassé.
  • Que faire : mettre à jour l'extension ; s'il n'y a pas de mise à jour, envoyer la ligne du journal à son auteur ; si l'extension est abandonnée, la remplacer.

5. Les questions à poser à votre hébergeur

  • Vers quelle version de PHP allez-vous migrer mon site, et à quelle date ? Le ferez-vous automatiquement ?
  • Puis-je changer de version moi-même dans le panneau, et revenir en arrière en cas de problème ? Jusqu'à quand ?
  • Proposez-vous un support prolongé payant pour les anciennes versions, et à quel prix ?
  • Ai-je droit à un site de test (staging) ? Comment le créer ?
  • Où voir le journal d'erreurs PHP ?
  • Comment restaurer une sauvegarde, et jusqu'à quelle date remontent-elles ?

Récapitulatif

  • Version de PHP actuelle notée (Santé du site)
  • Sauvegarde faite, restauration testée ou connue
  • WordPress, extensions et thèmes à jour
  • Analyse faite, erreurs examinées (avertissements plus tard)
  • Copie de test passée sur la nouvelle version et testée, journal lu
  • Site en ligne migré ; vous savez comment revenir en arrière
